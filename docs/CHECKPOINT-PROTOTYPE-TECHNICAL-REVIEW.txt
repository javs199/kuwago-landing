4. QUÉ VERIFICA ANTES DE ACEPTAR EL CHECKPOINT

A. Obtiene el recibo auténtico en memoria y comprueba etapa/edad.
B. Exige callbacks de evidencia y observación; inspect(4) valida identidad fija,
   esquema aprobado, historial exacto, semillas, ausencia de contenido,
   PRAGMA quick_check y foreign_key_check.
C. Lee el historial y reconstruye el resultado esperado en workerd local efímero:
   restaura el backup cifrado aprobado de etapa 3, verifica sus hashes y aplica
   allí el SQL ORIGINAL de 0004. Nunca repite ese SQL en el remoto.
D. Solo applied_at de la fila nueva 0004 se toma del historial observado y se
   comprueba en una ventana temporal acotada. En el prototipo la ventana es
   ACK local menos 20 segundos hasta ACK, con la tolerancia de un segundo del
   validador. Se compara todo lo demás, incluidos tipos, filas, schema, fechas
   previas y sqlite_sequence. No se adopta el remoto como su propio oráculo.
E. Compara un snapshot posterior completo contra esa proyección exacta.
   Una diferencia lógica termina la operación sin elegir una referencia distinta.
F. Solo DESPUÉS toma el bookmark candidato de la nueva ventana y exige recibo
   de persistencia protegido con hash. Es una fase de validación seguida de una
   fase de checkpoint, no un catch que ignore un error anterior de concurrencia.
G. captureBatchBaseline() exige enlace exacto al candidato, dos snapshots completos
   iguales al fingerprint esperado y tres bookmarks iguales (first/middle/last).
   Guarda observaciones incluso cuando falla. No tiene bucle de estabilización.
H. assertVerifiedBaselineCurrent() exige edad menor de 30 segundos del baseline
   y una última igualdad de bookmark antes de devolver el checkpoint.

La frontera posterior a la validación permite reconocer un estado nuevo causado
por una escritura propia respecto del estado PREVIO. NO permite ignorar un cambio
dentro de la ventana NUEVA. Si cambia el candidato frente a first, hay diferencia
lógica, first/middle/last no coinciden o falla la evidencia: se detiene sin rebase
silencioso ni reintento. Puede volver a bloquear legítimamente; no se garantiza
que elimine todos los avances de Time Travel observados en producción.

5. DETECCIÓN DE CONCURRENCIA Y LÍMITES

Detecta diferencias persistentes contra el resultado esperado, snapshots distintos,
cambios de bookmark desde la frontera candidata y fallos de la evidencia.
El escritor existente conserva guardas SQL dentro del batch: esquema, historial,
semillas y todas las filas/tipos del snapshot, incluido ledger/secuencias. Una
carrera posterior a la última lectura que cambie esos datos hace abortar el CHECK
antes de aplicar la migración siguiente. El prototipo NO reemplaza esas guardas.

NO OFRECE:
- Un bloqueo distribuido, exclusión de todos los operadores, aislamiento serializable
  entre múltiples peticiones REST ni atribución de cada escritura a un actor.
- Prueba de ausencia de cambios transitorios que otro actor haga y revierta antes
  de la ventana comprobada o entre lecturas dejando exactamente el mismo estado.
- Prueba de que un cambio de Time Travel sea necesariamente una escritura de datos,
  ni que sea necesariamente causado por nuestra migración.
- Un bookmark causal de D1 Sessions API. Se usa Time Travel para recuperación.
- Un ACK persistente o no reutilizable: vive solo en memoria, ownWriteMetadata()
  no lo consume, no queda ligado a su transporte y puede ser consultado varias
  veces durante la vigencia. El prototipo no debe exponerse a llamadores no fiables.
- Prueba independiente del valor histórico exacto de applied_at de 0004: ese campo
  se observa y acota; dentro de su ventana temporal no existe una copia anterior
  con la que contrastarlo. Las fechas de las filas previas sí se preservan.
- Un límite absoluto de 20 segundos de ejecución SQL en el servidor: el timeout
  HTTP es una condición del cliente y no demuestra cancelación del commit remoto.
  La ventana ACK-20s es una heurística conservadora y puede rechazar casos válidos
  por latencia/reloj; requiere revisar marcas reales de inicio y ACK del batch.
- Evidencia durable garantizada por la función aislada: comprueba un resultado de
  callback con bookmarkProtected y hash. Un llamador interno incorrecto podría
  devolver esos campos sin persistir. Faltan pruebas de integración del callback

- Garantía de que el fingerprint representa datos que no cambiarán después del

- Compatibilidad general con 0005/0006. Está limitado a etapa 4; campos aleatorios
  como epoch de 0005 precisan un oráculo/validación específicos.
- Borrado físico absoluto de secretos en memoria administrada.

6. CÓMO SE EVITA REPETIR UNA MIGRACIÓN CUYO POSTFLIGHT FALLÓ

El prototipo SOLO LEE/VALIDA el resultado; no ejecuta la migración ni reintenta SQL.
La seguridad contra repetición procede del ejecutor/escritor ya existentes:
- Marcador persistente de intento creado con wx antes de usar el transporte; un ID
  consumido no se reinicia ni se reanuda aunque falte un postflight verificado.
- El recibo de preflight y el batch se consumen antes de enviar el SQL. Un error
  o respuesta ambigua no devuelve esa capacidad para reintentar.
- El transporte exige batches aprobados en orden, rechaza duplicados y bloquea
  nuevas escrituras tras fallo de su petición mutante.
- El runner detiene la secuencia al primer error; un postflight fallido no significa
  que el SQL haya fallado. Hay que distinguir intentada/aceptada de verificada.
- SQL de migración y fila d1_migrations se ejecutan en el batch transaccional. Una
  nueva ejecución no puede partir del esquema/historial previo si ya se aplicó.
- Para decidir el estado tras ambigüedad se requiere reconciliación de SOLO LECTURA,
  no repetir la migración. Un nuevo intento posterior necesita autorización y
  baseline/respaldo adecuados al estado confirmado; no basta cambiar el UUID.

Esto no es una garantía global exactly-once frente a todas las herramientas o
cuentas que puedan escribir D1. Tampoco autoriza recuperar o repetir una escritura
cuando el proceso pierde memoria o falla el disco: esos casos requieren revisión.
